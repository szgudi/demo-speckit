# 功能规格：Todo List

**功能编号**：001-todo-list  
**状态**：草案  
**创建日期**：2026-08-26  
**输入来源**：`需求.md`、`.specify/memory/constitution.md`

## 1. 目标与范围

提供一个中文界面的单页面 Todo List，让单个匿名用户能够集中记录待办事项，并持续更新其完成状态。待办数据是持久化的业务数据：用户刷新页面或重新打开应用后，已保存的内容与状态仍应可用。

本迭代包含：新增待办、查看待办、编辑待办标题、标记完成或恢复未完成、删除待办，以及界面的加载、空数据和错误反馈。

## 2. 用户故事与验收场景

### 用户故事 1：新增待办

作为一名用户，我希望输入并保存一条待办事项，以便记录需要完成的事情。

#### 验收场景

1. **成功新增有效待办**
   - **假如** 用户位于待办列表页面，且输入框中填写了未超过长度上限的有效标题
   - **当** 用户提交新增操作
   - **那么** 系统创建一条未完成的待办，并在列表中显示该标题
   - **并且** 成功提示或等效的可感知反馈会告知用户保存成功
   - **并且** 输入框会被清空，用户可以继续新增

2. **拒绝空白标题**
   - **假如** 用户没有输入内容，或输入内容仅由空白字符组成
   - **当** 用户提交新增操作
   - **那么** 系统不创建待办
   - **并且** 界面显示清晰的中文校验提示

3. **拒绝过长标题**
   - **假如** 用户输入的标题在去除首尾空白后超过 200 个字符
   - **当** 用户提交新增操作
   - **那么** 系统拒绝保存，不创建待办
   - **并且** 界面显示中文提示，明确说明标题最多只能包含 200 个字符

### 用户故事 2：查看待办列表

作为一名用户，我希望查看已保存的待办及其完成状态，以便了解当前需要处理的事项。

#### 验收场景

1. **显示已有待办**
   - **假如** 系统中已有待办数据
   - **当** 用户进入或刷新待办列表页面
   - **那么** 系统显示所有待办的标题和完成状态
   - **并且** 未完成待办显示在已完成待办之前
   - **并且** 同一状态下按创建时间从新到旧显示

2. **显示空数据状态**
   - **假如** 系统中不存在待办数据
   - **当** 用户进入待办列表页面
   - **那么** 系统显示中文空状态提示
   - **并且** 提示用户可以新增第一条待办

3. **显示加载与读取失败状态**
   - **假如** 页面正在读取待办数据
   - **当** 读取尚未完成
   - **那么** 系统显示加载状态，且不把加载中的状态误报为没有待办
   - **假如** 读取请求失败
   - **当** 系统收到失败结果
   - **那么** 系统显示中文错误提示和可执行的重新加载操作

### 用户故事 3：更新完成状态

作为一名用户，我希望标记待办为完成，或将其恢复为未完成，以便准确反映进度。

#### 验收场景

1. **标记为完成**
   - **假如** 列表中存在一条未完成待办
   - **当** 用户执行完成操作
   - **那么** 该待办的完成状态更新为已完成，并以可辨识的视觉样式反映该状态
   - **并且** 用户刷新页面后，该状态仍保持为已完成

2. **恢复为未完成**
   - **假如** 列表中存在一条已完成待办
   - **当** 用户执行恢复操作
   - **那么** 该待办恢复为未完成
   - **并且** 列表根据排序规则更新其位置

3. **状态更新失败**
   - **假如** 用户尝试更新待办状态但保存失败
   - **当** 系统收到失败结果
   - **那么** 系统显示中文错误提示
   - **并且** 列表保留服务器已确认的状态，避免显示错误的成功结果

### 用户故事 4：编辑待办标题

作为一名用户，我希望更正已有待办的标题，以便让记录保持准确。

#### 验收场景

1. **成功编辑标题**
   - **假如** 列表中存在一条待办
   - **当** 用户将其标题修改为符合规则的新标题并保存
   - **那么** 列表显示新的标题
   - **并且** 刷新页面后仍显示新标题

2. **取消编辑**
   - **假如** 用户正在编辑待办标题
   - **当** 用户取消编辑
   - **那么** 系统不保存未提交的修改，并恢复原始标题

3. **编辑校验失败**
   - **假如** 用户提交空白标题或超过 200 个字符的标题
   - **当** 系统校验输入
   - **那么** 系统不更新该待办，并显示对应的中文校验提示

### 用户故事 5：删除待办

作为一名用户，我希望删除不再需要的待办，以便保持列表整洁。

#### 验收场景

1. **确认后删除待办**
   - **假如** 列表中存在一条待办
   - **当** 用户发起删除并在确认操作中确认
   - **那么** 系统永久删除该待办，并将其从列表移除
   - **并且** 刷新页面后该待办不会重新出现

2. **取消删除**
   - **假如** 用户发起删除操作
   - **当** 用户在确认操作中取消
   - **那么** 系统不删除该待办

3. **删除失败**
   - **假如** 用户确认删除但请求失败
   - **当** 系统收到失败结果
   - **那么** 系统显示中文错误提示
   - **并且** 该待办继续保留在列表中

## 3. 业务规则与数据要求

- 待办至少包含：稳定的唯一标识、标题、完成状态、创建时间和最后更新时间。
- 标题在去除首尾空白后不能为空，长度为 1 至 200 个字符；保存时使用去除首尾空白后的标题。
- 新建待办默认处于未完成状态。
- 删除为永久删除；本迭代不提供撤销、回收站或历史版本。
- 任何针对不存在待办的更新或删除请求都必须失败，并返回可供界面识别的错误结果；界面应提示该待办已不存在并重新加载数据。
- 待办数据必须以 MySQL 为持久化来源；内存、浏览器本地存储或模拟数据不得作为生产业务数据的唯一来源。

## 4. 功能边界

### 纳入本迭代

- 单个匿名用户的单一待办列表。
- 待办的新增、查看、编辑、完成/恢复和删除。
- 数据持久化，以及与上述操作相关的加载、空数据、校验、成功和错误反馈。

### 不纳入本迭代

- 用户注册、登录、权限管理与多用户数据隔离。
- 多列表、分类、标签、优先级、截止日期、搜索、筛选和排序配置。
- 子任务、附件、评论、提醒、通知、共享协作、离线同步、导入导出和批量操作。
- 删除撤销、回收站、审计历史和数据统计。
- 原生移动端应用；本迭代仅交付 Web 单页面应用。

## 5. 非功能要求

### 技术与架构

- 前端必须使用 React 和 TypeScript 构建单页面应用；后端必须使用 Node.js 和 TypeScript；业务数据必须保存至 MySQL。
- 前后端职责分离：React 仅负责界面和通过 HTTP API 调用后端；Node.js 负责业务规则、输入校验和 MySQL 访问。前端不得直接连接数据库。
- 后端访问 MySQL 必须通过数据访问层或等效的受控边界，并使用参数化查询或 ORM 参数绑定，防止 SQL 注入。
- 前后端仅通过版本明确的 HTTP API 和清晰的数据传输结构通信。每项后端能力均须在后续计划中定义方法、路径、请求、成功响应、错误响应和状态码。
- 代码不得使用 `any`、无约束类型断言或忽略 TypeScript 错误；边界输入应使用 `unknown` 并进行运行时校验。

### 体验与可用性

- 界面文本、面向开发者的错误说明和本功能的文档均使用中文。
- 新增、编辑、切换完成状态和删除操作必须具有明确、可操作的控件，且其当前状态可被用户辨识。
- 页面必须明确处理加载、成功、空数据、输入校验和 API 失败，不能假定请求总会成功。
- 核心操作应可使用键盘完成；交互控件需要可访问的名称，状态与错误提示应能被辅助技术读取。
- 在常见桌面和移动浏览器的可视区域内，新增、查看和操作待办不应依赖水平滚动。

### 可靠性、测试与安全

- 已确认保存的数据在刷新页面后必须可重新读取；一次失败的写入不得伪装成成功，也不得破坏其他已保存数据。
- 后端必须校验所有外部输入，并使用一致且可供前端处理的错误结构返回失败结果；错误响应不得泄露数据库凭据、SQL 语句或内部堆栈信息。
- 后续实现必须为所有 API 提供自动化测试，覆盖正常路径、关键输入校验、未找到资源及主要失败场景。
- 后续实现必须提供端到端测试，至少覆盖用户在真实前后端 API 支持下新增待办、标记完成并在刷新后确认状态、删除待办的核心流程。
- 环境变量、数据库凭据和其他敏感信息不得提交到版本控制；后续实现须提供中文环境配置示例和启动说明。

## 6. 成功标准

当用户能够在浏览器中创建、查看、编辑、完成/恢复和删除待办，且这些变化经由后端 API 保存到 MySQL、刷新后保持一致，并且所有定义的验收场景及后续 API 与端到端测试通过时，本功能即满足交付条件。
