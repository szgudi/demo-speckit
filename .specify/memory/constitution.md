# Todo List 项目宪章

## 核心原则

### 一、既定技术栈

本项目必须采用 React 构建前端单页面应用，采用 Node.js 构建后端服务，并使用 MySQL 持久化业务数据。新增技术依赖必须与该技术栈兼容，并在相应的规格或计划文档中说明其用途；不得以其他前端框架、后端运行时或数据库替代上述核心技术。

### 二、前后端分离

前端与后端必须作为职责明确、可独立运行和测试的应用边界：React 前端仅负责界面呈现、用户交互与调用 API；Node.js 后端负责业务规则、数据校验、鉴权（如后续需要）及 MySQL 访问。前端不得直接连接 MySQL，后端不得依赖浏览器界面状态。双方只通过版本明确的 HTTP API 和约定的数据传输结构通信。

### 三、以 API 契约为中心

每一项可由前端调用的后端能力必须具备清晰的 API 契约，至少定义请求方法与路径、参数或请求体、成功响应、错误响应和状态码。接口实现变更必须同步更新相关规格、计划或接口文档，并保持向后兼容；若无法兼容，必须明确记录迁移方式。后端必须校验所有外部输入，并以一致、可供前端处理的错误结构返回失败结果。

### 四、测试是交付条件

所有 API 必须具备自动化测试，覆盖正常路径、关键输入校验及主要错误场景。项目必须提供端到端（E2E）测试，至少验证用户在浏览器中完成 Todo 的核心流程，并经由真实前后端 API 运行。功能在相关 API 测试和 E2E 测试通过前不得标记为完成；缺陷修复必须先补充能够重现该缺陷的测试，或说明无法自动化的原因。

### 五、TypeScript 类型安全

前端和后端代码必须使用 TypeScript。不得为规避类型检查而使用 `any`、不受约束的类型断言或忽略 TypeScript 错误；确有边界数据无法静态确定时，必须使用 `unknown` 并在运行时校验后再缩小类型。跨前后端传递的数据结构应使用共享类型或由同一契约生成，以避免重复定义导致的不一致。提交的代码必须通过 TypeScript 类型检查。

### 六、中文优先的工程沟通

所有项目文档、规格、计划、任务说明、面向开发者的错误说明以及代码注释必须使用中文。变量、函数、类型、接口、路由和文件名可使用符合行业惯例的英文命名，但其补充说明必须为中文。引入第三方英文材料时，必须在项目文档中提供中文说明，明确其与项目的关系。

## 技术与交付约束

- Todo 数据必须存储于 MySQL；不得将内存、浏览器本地存储或模拟数据作为生产业务数据的唯一来源。
- 后端必须通过数据访问层或等效的受控边界访问 MySQL，并使用参数化查询或 ORM 参数绑定，避免 SQL 注入。
- 前端必须明确处理 API 的加载、成功、空数据和错误状态，不能假定请求始终成功。
- 环境变量、数据库凭据和其他敏感信息不得提交至版本控制；须提供中文环境配置示例和启动说明。
- 每个功能迭代必须在 `specs/<编号>-<功能名>/` 中维护规格、计划与任务；实现进度应在任务文档中如实更新。

## 质量门禁与审查

在合并或交付任何功能前，必须至少完成以下检查：

1. TypeScript 类型检查通过。
2. 相关 API 自动化测试通过。
3. 相关 E2E 测试通过。
4. API 契约、实现与前端调用保持一致。
5. 文档与新增或修改的代码注释符合中文要求。

评审应优先拒绝绕过类型安全、跨越前后端边界、缺少测试或未更新契约的变更。对本宪章的例外必须在对应计划或变更说明中记录原因、影响范围、替代控制措施和恢复合规的期限。

## 治理

本宪章高于项目中的一般开发习惯、模板默认值和个人偏好。所有规格、计划、任务和代码审查均必须据此核验；若与本宪章冲突，应修改下级文档或实施方案以恢复一致。

修订本宪章必须说明变更原因、受影响的原则和迁移要求，并在下方更新版本与日期。采用语义化版本：新增或实质性强化原则时递增主版本；新增说明或扩展指导时递增次版本；仅文字澄清时递增修订版本。
